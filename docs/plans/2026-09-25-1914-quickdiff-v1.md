# QuickDiff v1 Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A minimal, keyboard-first VS Code extension that lists changed files in its own sidebar and opens them in VS Code's native diff editors, for the working tree, a branch against its base, or two refs, with a terminal entry point.

**Tech Stack:** Node 24 and rite via mise (`.mise.toml`), rite (`rite.edn`) as task runner, TypeScript (strict, plain `tsc`, no bundler), VS Code Extension API 1.95, bundled `vscode.git` extension API, Vitest for pure modules, Mocha inside a real VS Code via `@vscode/test-cli` under `xvfb-run` for integration tests, `@vscode/vsce` for packaging.

---

## Design

### Vision

Open a repo and immediately see what changed. Move between files and hunks from the keyboard. Nothing else. Inspired by revdiff.com and the Cursive diff viewer. No structural diff, no staging, no comments, no review workflow.

### Approach

The extension owns three things: a **changes model**, a **flat file list** in its own activity bar container, and **keyboard commands**. All rendering is delegated to VS Code's diff editor (`vscode.diff`) and multi-diff editor (`vscode.changes`). Git data comes from the bundled git extension's API (`vscode.git`, API version 1), never from a shelled-out `git`, so refs, renames, and encodings are already handled.

### Modes

| Mode | Left ref | Right ref | File list source |
|------|----------|-----------|------------------|
| `worktree` | `HEAD` | working tree file | `repo.diffWithHEAD()` (staged + unstaged tracked changes) plus untracked files from `repo.state.workingTreeChanges` and `repo.state.untrackedChanges` with status `UNTRACKED` |
| `branch` with `base` | merge base of `base` and `HEAD` | `HEAD` | `repo.diffBetween(mergeBase, 'HEAD')` |
| `refs` with `from`, `to` | `from` | `to` | `repo.diffBetween(from, to)` |

Branch mode shows **committed** changes only, against the merge base (three-dot semantics, like a pull request). Uncommitted work belongs to worktree mode. If no merge base exists, the model reports an error and keeps the previous list.

The base branch comes from the request, else the setting `quickdiff.baseBranch`, else auto-detect: `main` if a local branch named `main` exists, otherwise `master`, otherwise ask via quick pick.

Mode is persisted per workspace in `workspaceState` under key `quickdiff.mode`. Default is `worktree`.

### Diff sides

For a file change and resolved refs, the opener builds:

- **left**: empty virtual document if the file is added or untracked; otherwise `api.toGitUri(originalUri, leftRef)`.
- **right**: empty virtual document if the file is deleted; otherwise the real file URI in worktree mode, or `api.toGitUri(renameUri ?? uri, rightRef)` in ref modes.

The empty document is served by a `TextDocumentContentProvider` for scheme `quickdiff-empty` that always returns `""`. The URI path mirrors the file path so the editor title is meaningful.

For the multi-diff editor, the tuple passed to `vscode.changes` is `[uri, left | undefined, right | undefined]`, where `undefined` marks a missing side.

### Hunks and navigation

Hunk positions come from parsing the unified diff text of a single file (`repo.diffWithHEAD(path)` or `repo.diffBetween(l, r, path)`, with `path` the absolute fs path). A hunk's position is the **modified-side line of its first `+` or `-` line**, not the hunk header start. Untracked and added files have a single hunk at line 1. Deleted files have a single hunk at line 1.

Navigation commands:

- `quickdiff.nextFile` / `quickdiff.prevFile`: open the next or previous file in the list, wrapping around. Opening a file places the cursor on its first hunk (or last hunk when arriving via `prevHunk`), centered.
- `quickdiff.nextHunk` / `quickdiff.prevHunk`: move the cursor to the next or previous hunk in the active file. Past the last hunk, jump to the next file's first hunk. Before the first hunk, jump to the previous file's last hunk.
- The "current file" is derived from the active tab: if it is a `TabInputTextDiff` whose `modified` (or `original`, for deleted files) URI matches one of the list entries, that entry is current. Otherwise `nextFile` starts from the first entry.

In the multi-diff editor (single screen mode) the native `multiDiffEditor.goToNextChange` / `multiDiffEditor.goToPreviousChange` commands already span files. When the active tab is a QuickDiff multi-diff editor, `nextHunk` / `prevHunk` delegate to those commands and `nextFile` / `prevFile` do the same, so the chords keep working without a mode switch. The multi-diff tab is recognised by its label: every QuickDiff multi-diff title starts with the constant `MULTI_TITLE_PREFIX = 'QuickDiff: '`. The `TabInputTextMultiDiff` type is still proposed API and must not be referenced anywhere; a tab whose `input` is not `TabInputText` or `TabInputTextDiff` and whose label starts with the prefix is the multi-diff tab.

If the active text editor is the **original** side of a diff (its document URI equals the left URI), the extension first runs `workbench.action.compareEditor.focusOtherSide`, re-reads `window.activeTextEditor`, and only then reads or moves the cursor. If after that the active editor is still not the right side, it re-opens the diff via `openFile(file, { hunk: 'first' })` instead of guessing.

### Sidebar

Activity bar container `quickdiff` with a single view `quickdiff.files` titled "Changes". Flat list sorted by path. Each row: file name as label, directory as description, a status icon (`diff-added`, `diff-modified`, `diff-removed`, `diff-renamed`), and `resourceUri` set so VS Code applies git color decorations. Clicking a row runs `quickdiff.openFile`. The view `description` shows the mode label, e.g. `working tree`, `feature → master`, `abc123..def456`. The view `badge` shows the file count. When the list is empty, the view `message` says `No changes`. The selection follows the active diff editor.

View title actions: refresh, pick mode, open all.

### Terminal entry

The `bin/qd` shell script builds `vscode://abogoyavlensky.quickdiff/open?<query>` and runs `code --open-url <url>`. The query carries `cwd` (git top-level of the current directory), `mode`, and mode parameters, plus optional `view=all`. `qd` with no arguments is worktree mode, `qd <base>` is branch mode, `qd <from> <to>` is refs mode, `-a` opens the multi-diff editor. `--print-url` prints the URL and exits, which is how it is tested.

The extension's `UriHandler` parses the query and decides via a pure function:

```ts
type OpenPlan =
  | { action: 'apply'; request: OpenRequest }
  | { action: 'openFolder'; folder: string; request: OpenRequest }
  | { action: 'reject'; reason: string };
function planOpen(request: OpenRequest, workspaceFolders: string[]): OpenPlan;
```

The `workspaceFolders` argument is `[repositoryRoot]` when the model has a repository, otherwise the fs paths of `workspace.workspaceFolders` (which is empty in an empty window). So `apply` happens only when `cwd` is inside the repository QuickDiff is bound to. Otherwise `openFolder`: the request is stored in `globalState` under `quickdiff.pendingOpen` with a timestamp, then `vscode.openFolder` is executed in the same window, which replaces the window content and restarts the extension host. On activation the extension replays a pending request younger than 2 minutes whose `cwd` is inside the bound repository, and always clears the key. Applying a request sets the mode, refreshes, focuses the list, and opens the first file, or the multi-diff editor when `view=all`. A second repository inside a multi-root window is therefore opened as its own folder; v1 binds to one repository per window.

The URI handler, commands, and the view are registered unconditionally at activation, before and independent of repository discovery. When no repository is found, `ready` still resolves, the context key `quickdiff.noRepository` is set, the view shows its welcome message, and any command that needs the model shows `QuickDiff: no git repository in this window`. The `openFolder` branch of the handler works without a model, which is what makes `qd` usable from an empty window.

The command `quickdiff.installCli` copies `bin/qd` to `~/.local/bin/qd`, makes it executable, and shows a message with the path. Windows is out of scope for the script.

### Activation

`activationEvents`: `onUri`, `onStartupFinished` (for pending-request replay). Views and commands activate on their own. `extensionDependencies`: `vscode.git`. On activation the extension registers everything first, then waits for the git API state `initialized` and for a repository covering the first workspace folder (`api.getRepository`, else `onDidOpenRepository` with a 10 s timeout). Discovery failure is not an activation failure: it resolves to "no repository" as described under Terminal entry.

Refreshes are guarded against races: `ChangesModel.refresh` increments a sequence number before awaiting git and discards its result if the number changed while it was in flight, so a slower older refresh never overwrites a newer mode's list.

### Error handling

Git API errors surface as `window.showErrorMessage` with the mode label and the git message, and the model keeps its last good list. Navigation commands with an empty list show `No changes` in the status bar for 2 s. All async command handlers are wrapped so a rejection never becomes an unhandled promise.

### Testing strategy

- **Unit (Vitest)**: everything under `src/core/`, which must not import `vscode`. Also the `qd` script via `--print-url`.
- **Integration (Mocha in VS Code)**: `@vscode/test-cli` launches a real VS Code with the extension and a generated fixture repository as the workspace, under `xvfb-run -a`. The extension's `activate` returns a test API:

```ts
export interface QuickDiffApi {
  ready: Promise<void>;                      // repository discovery finished (found or not), first refresh done
  model: ChangesModel | undefined;           // undefined when no repository was found
  filesProvider: vscode.TreeDataProvider<FileChange>;
  treeView: vscode.TreeView<FileChange>;
  handleUri(uri: vscode.Uri): Promise<void>;
}
```

  Tests drive commands with `vscode.commands.executeCommand`, then assert on `model.files`, `window.tabGroups` tab inputs, `window.activeTextEditor.selection`, and `treeView.selection`.

- **Fixture repository** (built by `test/fixture/makeRepo.mjs`, deterministic, `git init -b master`):
  1. Commit 1 on `master`: `a.txt` (10 lines `a1`..`a10`), `src/b.ts` (20 lines `b1`..`b20`), `deleted.txt` (3 lines).
  2. Branch `feature` from commit 1. Commit 2 on `feature`: change `src/b.ts` line 3 to `b3-changed` and line 15 to `b15-changed`, add `new.txt` (2 lines), delete `deleted.txt`.
  3. Commit 3 on `master`: change `a.txt` line 1 to `a1-master`.
  4. Checkout `feature`. Working tree: change `a.txt` line 9 to `a9-wip` (unstaged), change `src/b.ts` line 18 to `b18-staged` and `git add` it, create `untracked.txt`.

  Expected lists:
  - worktree: `a.txt` M, `src/b.ts` M, `untracked.txt` U. Hunks: `a.txt` [9], `src/b.ts` [18], `untracked.txt` [1].
  - branch base `master`: `deleted.txt` D, `new.txt` A, `src/b.ts` M. `a.txt` must be absent (proves merge-base semantics). Hunks for `src/b.ts`: [3, 15].
  - refs `master~1` → `master`: `a.txt` M, hunk [1].

- **Not automated**: quick pick interaction, the real `code --open-url` hop, `vscode.openFolder` reload. These are on the manual F5 checklist in the last task.

### Task 3: Core hunk parsing and stepping

**Files:**
- Create: `src/core/hunks.ts`
- Test: `test/unit/hunks.test.ts`

- [ ] **Step 1: Write tests**
  `parseHunkLines(diff: string): number[]` with hand-written unified diffs:
  - one change at line 3 with 3 lines of context (`@@ -1,6 +1,6 @@`, two context lines, `-b3`, `+b3-changed`) → `[3]`.
  - two hunks at 3 and 15 → `[3, 15]`.
  - pure deletion of old line 5 (`@@ -3,5 +3,4 @@`, two context lines, then `-`) → `[5]`.
  - insertion at top of file (`@@ -0,0 +1,2 @@`) → `[1]`.
  - empty string → `[]`.
  - header lines (`diff --git`, `index`, `---`, `+++`) are skipped and not mistaken for changes.
  `nextHunkLine(hunks, currentLine)`: first hunk strictly greater than `currentLine`, else `undefined`. `prevHunkLine`: last hunk strictly less, else `undefined`.

- [ ] **Step 2: Run tests, expect failure**

- [ ] **Step 3: Implement**
  Walk lines. On `@@ -a[,b] +c[,d] @@` set `modifiedLine = c` and `inHunk = true`, `recorded = false`. Inside a hunk: line starting with `+` (not `+++` header, which only appears before the first `@@`) → if not recorded, push `modifiedLine`, mark recorded; increment `modifiedLine`. Line starting with `-` → if not recorded, push `max(modifiedLine, 1)`, mark recorded; do not increment. Line starting with space → increment. `\ No newline at end of file` → ignore. Once past the first `@@`, treat every line as hunk body.

- [ ] **Step 4: Run tests, expect pass**

- [ ] **Step 5: Commit**
  `git commit -m "feat(core): parse hunk positions from unified diff"`
